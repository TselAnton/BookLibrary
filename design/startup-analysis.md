# Замеры запуска BookLibrary

## Прогрев кеша обложек — 21 октября 2026

Кеши миниатюр и больших обложек уже были разделены в памяти, но оба использовали
общую очередь из двух потоков. Поэтому открытая карточка могла ждать окончания
запросов таблицы и показывать заглушку. Теперь `resolveCover` синхронно читает
изображение карточки до возврата из метода и сохраняет его в отдельном кеше памяти.
Повторное открытие использует готовый результат; неудачное чтение повторяется.
Карточка продолжает использовать привязку к `ImageHolder.imageProperty`.

Таблица хранит декодированные миниатюры до 24 × 32 пикселей, карточка — изображения
до 488 × 740 с сохранением пропорций. Большие обложки запрашиваются только при
открытии карточек. Дискового кеша нет. Смена пути заменяет запись соответствующего
кеша; явное инвалидирование после редактирования очищает оба кеша и отменяет
устаревшие фоновые запросы.

Число фоновых потоков увеличено до `min(4, availableProcessors())`; внешние файлы
читаются через `BufferedInputStream`. Контрольный замер только чтения/декодирования
показал медианы 2154 мс для двух потоков без буфера, 2064 мс для двух с буфером,
1122 мс для четырёх без буфера и 1092 мс для четырёх с буфером. Основной выигрыш
даёт параллельное декодирование, вклад буфера небольшой.

Полный прогрев `ImageProvider`, включая публикацию результатов в потоке JavaFX:

| Реализация | Три запуска, мс | Медиана, мс |
| --- | --- | --- |
| До изменения: два потока | 2130,0 / 2115,0 / 2144,4 | 2130,0 |
| После изменения: четыре потока и буфер | 1135,6 / 1145,1 / 1143,0 | 1143,0 |

Сокращение — около 46%, ускорение — 1,86 раза. Каждый полный замер выполнен
в отдельной JVM с Amazon Corretto 17.0.13 и JavaFX 21.0.12. Начало — перед
постановкой запросов всех книг, конец — снятие `isLoading` у последнего запроса.
Инициализация JavaFX, JSON и создание провайдера в интервал не входят. Кеш ОС
не сбрасывался; это холодный кеш приложения, не холодный диск после перезагрузки.

Текущий `test_data/repository/bookStorage.json` содержит 849 книг, все 849 обложек
загрузились в каждом замере. Это отличается от прежнего набора из 851 книги ниже.
Предупреждение о повреждённом сегменте JPEG осталось, но декодирование завершилось.
Повторный проход по 849 прогретым записям занял 0,71–0,93 мс после изменения.
Сумма пикселей миниатюр — 2 297 760 байт (около 2,19 МиБ при четырёх байтах
на пиксель), без объектов JavaFX, текстур и временной памяти декодера.

Проверки `ImageProviderTest` охватывают синхронную карточку при намеренно
заблокированном загрузчике таблицы, разные размеры и объекты двух кешей, повторное
использование, инвалидирование, повтор чтения после появления файла, ошибки,
привязки изображений, запоздалые callbacks и закрытие загрузчика.
Полная проверка `mvn clean package` успешна: 135 тестов прошли, четыре пропущены,
включая успешное выполнение тестов окон JavaFX.

Приоритет видимых строк реализован следующим этапом, описанным ниже.
Увеличение числа потоков сверх четырёх требует отдельных замеров нагрузки
и памяти. Синхронное открытие непрогретой карточки по-прежнему занимает время чтения
одного исходного файла; на медленном или сетевом диске интерфейс ждёт это чтение.

### Приоритет видимых строк

`VisibleCoverPriority` получает первую и последнюю видимые строки через публичный
API `VirtualFlow` после layout JavaFX. Это учитывает частично видимые строки,
прокрутку, сортировку, фильтры, замену DTO и изменение размера окна. Скрытые
служебные ячейки, создаваемые таблицей для измерения, в снимок не входят.
Загрузчик получает новый набор ID только при изменении состава видимых строк.
При отсоединении таблицы приоритет сбрасывается; закрытие главного окна снимает
слушатель pulse и слушатель смены сцены.

`CoverLoadExecutor` использует ограниченное число потоков и приоритетную очередь.
Видимые книги выполняются перед фоновыми, внутри каждой группы сохраняется порядок
поступления. При смене экрана старые видимые запросы возвращаются к обычному
приоритету. Задача извлекается из очереди перед изменением ключа сортировки и
возвращается в ту же очередь; нового запроса чтения не создаётся. Отменённые
задачи удаляются из очереди, а новые запросы уже видимых книг сразу получают
повышенный приоритет, в том числе после инвалидирования кеша.

До первого layout могут начаться максимум четыре фоновых чтения. Они, как и
чтения, уже начавшиеся во время прокрутки, не прерываются: приоритет действует
на ожидающую часть очереди. Полный фоновый прогрев продолжается, поэтому фильтр
наличия обложки по-прежнему получает результаты и для невидимых книг. Размеры
изображений и разделение кешей памяти не изменены.

Детерминированные проверки блокируют рабочий поток, переставляют приоритеты и
проверяют порядок завершения без временных порогов. Отдельный тест с настоящим
окном таблицы проверяет снимки после прокрутки, сортировки, изменения высоты,
фильтрации, очистки списка, отсоединения и повторного присоединения таблицы.
Замеры времени в предыдущем разделе относятся к этапу увеличения числа потоков;
они не являются отдельным измерением времени появления видимых строк.

## Предыдущие замеры запуска — 19–20 октября 2026

После переноса загрузки обложек в фон библиотека из 851 книги открывается за 1,51 секунды вместо 5,25 секунды. Миниатюры и карточка сначала показывают контрастную обложку по умолчанию и автоматически заменяют её изображением книги. Книги без доступной картинки сохраняют общую обложку.

Медиана готовности сцены сократилась на 3738 мс, примерно на 71%. Полное чтение изображений продолжается после показа окна и в этот интервал не входит. Проверка реального окна отдельно дождалась завершения всех 851 запроса: все 851 изображения заменили placeholders, каждая миниатюра совпала с результатом своего запроса. В карточке проверен переход от общей обложки к изображению сущности без пересоздания окна. Снимки сохранены в `target/startup-analysis/async-*.png`.

Чтение файлов, проверка пути и декодирование выполняются в двух фоновых потоках `book-cover-loader`. Результат публикуется в потоке JavaFX через [Platform.runLater](https://openjfx.io/javadoc/21/javafx.graphics/javafx/application/Platform.html#runLater(java.lang.Runnable)), а `ImageView.imageProperty` привязано к состоянию загрузки. UI не ожидает окончания запроса и не проверяет существование внешних файлов синхронно. Кеш различает книгу и путь; изменение пути или сохранение редактируемой книги отменяет старые запросы. Завершение приложения закрывает загрузчик. Отсутствующий, повреждённый или недоступный файл оставляет общую обложку.

Общая обложка — `src/main/resources/com/tsel/home/project/booklibrary/img/default-book-cover.png`: крупная перечёркнутая книга цвета слоновой кости на тёмном шалфейном фоне. Она сгенерирована встроенным image_gen по [сохранённому запросу](references/default-book-cover-prompt.txt). Один объект изображения используется всеми placeholders, отдельно для каждой книги ресурс не декодируется.

Проверки: `mvn package` — 59 тестов прошли, 3 существующих теста отключены. Тесты фонового загрузчика проверяют отзывчивость FX-очереди при заблокированном рабочем потоке, замену всех привязанных изображений, кеш, ошибочные файлы, изменение пути, замену файла по тому же пути, запоздалое завершение отменённого запроса и закрытие загрузчика.

## Условия замера

Замеры выполнены 19 октября 2026 года на этой Windows-машине: Amazon Corretto 17.0.13, JavaFX 21.0.12, запуск собранного `target/BookLibraryApp.jar`. Для каждого варианта запускались три отдельные JVM последовательно. Файловый кеш ОС не сбрасывался: это запуск нового процесса, а не замер после перезагрузки компьютера.

Использованы отдельные копии `repository` и `.properties` в `target/startup-analysis`. Основной набор взят из `test_data`: 851 книга, у всех 851 существует файл обложки. Изображения читались по существующим абсолютным путям. В контрольной копии тех же данных только `coverImgAbsolutePath` заменён на `null`. Малый набор взят из корневого `repository`: четыре книги. Исходные хранилища и обложки не изменялись.

Конец замера — первый post-layout pulse после завершения `startScene`. Это готовность сцены после layout; момент физического вывода кадра на монитор отдельно не измеряется. `JVM uptime` включает время до входа в `App.main`, в том числе инициализацию логирования. Сборка Maven в эти числа не входит.

## Причина задержки до изменения

Цепочка вызовов до `stage.show`:

```text
MainViewController.configure
  updateTableColumns / refreshGenres / обработчики изменения genreFilter
    applyFilters
      getDtoBooks
        BookConverter.convert
          BookDTOBuilder.cover
            ImageProvider.resolveSmallCover
              new Image(url, 24, 32, true, true, false)
```

Последний аргумент `false` задавал синхронную загрузку. Все обложки читались и декодировались в JavaFX Application Thread до появления окна, хотя таблица показывает лишь часть строк. Размер результата 24 × 32 не устранял затраты на декодирование исходных JPEG и PNG.

Три прохода DTO возникают при инициализации фильтра жанра: `refreshGenres` сначала сбрасывает список на «Все жанры», затем восстанавливает выбор. Уже установленные listeners вызывают `applyFilters`; после `refreshGenres` метод `updateTableColumns` вызывает его ещё раз. Существующий кеш обложек сокращает расходы второго и третьего проходов, но объекты DTO, CheckBox и ImageView создаются повторно.

Отдельный запуск с JFR `settings=profile` подтвердил стеки `JPEGImageLoader.startDecompression`, `JPEGImageLoader.decompressIndirect`, `PNGImageLoader2` и `SmoothMinifier` в цепочке загрузки изображений. В записи 151 из 338 execution/native samples содержит JPEG или PNG decoder. Это выборка стеков, а не процент общего времени: запись также включает ожидание после старта. Суммарная длительность 21 события GarbageCollection около 94 мс. JFR-запуск не включён в таблицу трёх обычных замеров.

При чтении набора JavaFX выдаёт предупреждение `Corrupt JPEG data: premature end of data segment`. Эти файлы оставлены в замере как часть исходных данных.

## Оставшиеся затраты

Три прохода построения DTO при обновлении жанров сохраняются, но теперь вместе занимают около 111 мс вместо 3941 мс. Устранение промежуточных применений фильтра остаётся отдельной оптимизацией. Все миниатюры загружаются в фоне с ограничением числа рабочих потоков; полноценное изображение карточки запрашивается при её открытии.

Архивирование, JSON и очистка справочников дают значительно меньший вклад. Перенос архивации требует отдельно сохранить порядок создания резервной копии перед очисткой данных.

## Статус диагностики

Результаты выше получены временными замерами во время диагностики. После проверки асинхронной загрузки дополнительный код измерения времени удалён. Отчёт сохраняет результаты сравнения до и после изменения; для нового профилирования можно использовать штатный Java Flight Recorder без добавления измерений в приложение.
