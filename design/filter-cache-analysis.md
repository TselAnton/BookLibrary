# Анализ кеша фильтров

## Потоки и карты

| Состояние | Владелец | Решение |
| --- | --- | --- |
| Условия, черновик, редакторы, чекбоксы | JavaFX-поток | Обычные карты; concurrent-коллекция не разрешает доступ к контролам из фонового потока |
| Последние запросы `FilterOptionCache.queries` | Поток, создавший кеш | `LinkedHashMap` с LRU; публичные методы проверяют поток владельца |
| Метаданные и реестры типов/редакторов | Инициализация, затем чтение | Размер зависит от числа полей и обработчиков, а не от числа книг |
| Снимок значений и готовые результаты | Передаются между потоками | Неизменяемые копии карт/списков, публикация через `CompletableFuture` |
| Промежуточные домены и счётчики | Конкретный фоновый расчёт | Локальные карты, не разделяемые с UI или другим расчётом |

Массовая замена на `ConcurrentHashMap` не нужна. Она не обеспечила бы атомарность операций «проверить снимок — отменить старые запросы — заменить индекс» и убрала бы порядок доступа, нужный LRU. Общий изменяемый кеш обслуживает один поток, фоновый исполнитель получает только снимки. Нарушение контракта теперь обнаруживается сразу.

## Удержание памяти

Кеш удерживает один текущий индекс и не более восьми наборов результатов по условиям. При изменении каталога старые запросы отменяются, карта очищается; одинаковые снимки сохраняют прогретый индекс. Закрытие отменяет запросы, обнуляет ссылку на индекс и завершает исполнитель. Панель освобождает исходный список DTO, редакторы и их узлы. Уже выданный потребителю результат остаётся доступным, пока сам потребитель его использует.

Исправлена ссылка на завершённый `CompletableFuture<Index>`: раньше после `close()` он мог продолжать удерживать снимок, несмотря на очистку остальных полей.

`WeakHashMap` не является механизмом очистки при превышении памяти: его ключи могут исчезнуть при обычной сборке мусора, как только нет внешних сильных ссылок. Карты условий запросов создаются временно, поэтому такой кеш терял бы прогретые результаты даже при свободной памяти. Слабые ссылки также не помогают, если те же данные нужны открытому редактору или текущему индексу.

`SoftReference` для необязательных готовых результатов возможен, но момент очистки определяется JVM и не задаёт надёжный бюджет памяти. Пока оставлен предсказуемый LRU с явной очисткой. Восемь результатов ограничивают число записей, а не байты: объём результата зависит от количества уникальных значений. При выявленной профилированием проблеме следующий шаг — LRU с бюджетом по суммарному числу вариантов или размеру данных; слабые ссылки для всех карт этого не заменяют.

## Проверки жизненного цикла

`FilterOptionCacheTest` проверяет фоновое вычисление, повторное использование, создание/изменение/удаление записей, отклонение устаревшего результата, LRU и доступ только из потока владельца. `SageViewsTest` создаёт книгу через реальное окно, меняет её автора и цену, удаляет с подтверждением и проверяет таблицу, домен авторов и счётчики при сохранённых фильтрах. Проверяются специальные состояния цены.

## Аудит зависимостей

Старого движка поиска, командных алиасов, операндов и поиска подстроки цифр в рабочем коде больше нет. Удалены неиспользуемые JavaFX Web, ControlsFX, FormsFX, ValidatorFX, Ikonli, BootstrapFX, TilesFX и Maven Assembly/Shade из runtime-зависимостей. Shade остаётся плагином сборки. Lombok используется только при компиляции, JSR-305 объявлен явно. Старые assertions переведены на уже используемый JUnit Jupiter вместо случайного транзитивного JUnit из Maven-плагинов.

`Reflections` сохранён: `StorageBackupArchiver` использует его для обнаружения хранилищ с аннотацией `FileStorageName`. Удалять библиотеку вместе со старым поиском нельзя без отдельной переработки архиватора.
